# AI 辅助使用与真实性规范

本项目允许 AI 辅助设计、编码、测试和文字整理，但最终责任属于提交者。AI 不是团队成员，其输出不能替代人工理解、代码审查、实物验证和课程要求。若课程另有更严格规定，以课程规定为准。

## 允许的辅助与必须的人工作业

| 用途 | 可以辅助 | 人工必须完成 |
| --- | --- | --- |
| 架构与协议 | 比较方案、生成消息样例、检查遗漏 | 确认 UNO R4 WiFi 能力、实际传感器与接口边界，评审 MQTT/HA 契约 |
| 代码与配置 | 生成骨架、测试、注释和候选修复 | 阅读并理解关键逻辑，核对依赖/API，去除虚构接口，运行适用验证 |
| 分析与实验 | 生成分析脚本、模拟数据、实验设计 | 确定来源、指标和分母，采集真实数据，复算统计，明确限制 |
| 文档与展示 | 结构建议、语言润色、图表草稿 | 核对事实、引用、贡献与现状，区分真实、模拟和计划 |

不得让 AI 虚构传感器型号、人员身份、已部署组件、硬件连接、实验数值、测试通过结果或参考文献。不能把 AI 生成的图表或日志冒充现场观测。任何示例结果都必须标注为示例，不填写到实测结果栏。

## 记录粒度

**不记录每次聊天。** 对影响架构、关键逻辑、实验结论或较大文档内容的实质性使用做一条简要记录即可，可放在相关 PR 或本页“实际记录”区。连续围绕同一任务的多轮交流合并记录；不用保存完整聊天历史或逐条提示词。

工具与模型版本只记录实际知道的信息；无法确认时写“版本未记录/未知”，不猜测。被完全丢弃且未影响交付的建议通常不必记录，课程另有要求除外。

## 简要记录模板

```text
记录 ID / 日期 / 提交者 / 关联 issue 或 PR：
工具：实际使用的工具名称；已知模型/版本，未知则注明
目的：要解决的问题与预期用途
生成：采用了哪些代码、测试、配置、图表或文字；涉及的文件/片段
人工修改：实际做了哪些核对、重写、删减与设计判断；未修改也应如实写明
验证：实际执行的命令/人工复核方法、结果与证据；未运行及其原因
限制与后续：仍待实物验证、兼容性核查或隐私审查的内容
```

核心字段是 **工具 / 目的 / 生成 / 人工修改 / 验证**，不能只写“使用 AI 提高效率”。记录中的“人工修改”必须由实际提交者确认，AI 不能代为声称已检查、已理解或已验收。

## 验证底线

- 代码按 [开发流程](development.md) 执行适用验证；测试命令存在不等于已运行，测试通过也不代表真实系统已部署。
- 实验依照 [实验方案](experiments.md) 记录数据来源、计时条件和丢包分母；模拟与人工构造数据不包装成实测。
- Hermes 的报告本身也是待核查输出：注明时间范围、缺测和不确定性，结论应可追溯到输入。
- AI 辅助不能改变系统安全边界：分析只读 MQTT 遥测镜像，Agent/交互的任何控制只经 HA；未知设备与不支持的动作应拒绝，不补造执行成功信息。
- 外部建议中的安装命令、依赖、许可证、API 地址和权限申请需人工核对，不能无审查执行或扩大访问权限。

## 数据与密钥

不向外部 AI 上传住户身份、寝室号、作息信息、未经同意的原始遥测、WiFi 口令、broker 凭据、HA token 或其他秘密。用去敏的最小样例或明确标注的模拟数据说明问题；也要检查日志、截图和提示词中是否夹带敏感内容。

- **烧录与后续实测**：用户重新连接 USB 并明确同意后上传成功。启动 NEC 自检捕获 68 个边沿但识别 UNKNOWN，初次保护流程未发送 GREE；承接尚未使用的一次获准 GREE 复测后，发送回执与接收事件均记录 142 个边沿，结果仍为 UNKNOWN、ac=none。缓存进入解码事件路径的修复生效，完整目标状态与空调响应均未通过，已停止追加发码。

### AI-2026-11-05-IR-RAW-TIMING

- **工具与目的**：DeepSeek Harness / Codex；用户要求继续排查后，为既有一次 NEC 启动自检加入有界时序导出，定位 UNKNOWN 的可验证原因。保留上一轮成功发送后的接收缓存修复。
- **生成内容**：[C3 格式化器](../firmware/esp32-c3-ir/include/ir_raw_timing.h)、[发布路径](../firmware/esp32-c3-ir/src/main.cpp)及[离线分析器](../firmware/esp32-c3-ir/tools/nec_timing.py)与回归。最多 160 项、每包 16 项、固定 2 μs tick；从库保存缓冲发布，再发送普通接收事件。只由内部启动调用的显式参数启用，避免命令 ID 冒充启动来源。同步[事件说明](mqtt-protocol.md)；未改变遥测 Schema、ACL 或服务配置。
- **离线验证**：新增头文件前 native 构建按预期失败，之后 6 项通过；主机 handler、实际发布函数及分析器共 19 项通过，来源修正后发布测试再通过。固定 C3 目标编译通过。独立源码审查确认保存缓冲生命周期、分包上限和无额外发射调用；没有把源码审查或合成测试称为物理验证。
- **实际采集**：上传一次成功，只使用原有校准及一次 NEC 自检，观察端发布 MQTT 命令数为 0。真实 5 个分包完整拼成 68 项，随后收到普通 UNKNOWN 接收事件；起始缓冲为空，无截断、溢出或存储上限值。原始样本和上传记录仅留私有目录。
- **分析结果**：第 0 项为非测量哨兵；其余 67 项中，仅第一位零空隙记录 1210 μs，偏离标称 560 μs 与当前零窗口 382–638 μs。真实固定库的主机 NEC/HASH 子集回放原数组得到同一 UNKNOWN 哈希；仅替换该一项的明确合成副本严格解出预期 NEC `0x5A02A55A`。原证据字节不变，对照没有发送或写入设备。这足以解释该样本为何拒绝，未证明异常间隔的发送/接收/采样根因。
- **限制与人工复核**：没有追加红外、空调试码、容差/载波/电源调整或 Git commit/push；空调兼容性仍未通过。源码与分析待提交者理解及复核，下一步实物测量须独立区分发送端时序与接收模块/中断记录，不能用合成修正冒充实物修复。
